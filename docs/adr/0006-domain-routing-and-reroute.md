# ADR-0006：域名归属判定与链路健康自动改道

- 状态：已接受（v0.13.0 落地）
- 日期：2026-10-22
- 取代：无
- 相关：[ADR-0003](0003-dns-chain-framework.md)（链路框架）、
  [ADR-0005](0005-remove-chinadns-ng.md)（双 dnsproxy 实例）

---

## 1. 背景与需求

ADR-0003/0005 落地后，分流规则只有两个来源：

1. **SSR-Plus 的 gfw 名单**（`gfw_list.conf`，实测 3.5 万行）
2. **框架自己生成的静态片段** `dnschain-split.conf`

用户提出五条需求：

| # | 需求 | 落在本 ADR 的哪一节 |
|---|---|---|
| 1 | UI 新增「国内域名」「国外域名」两个自定义输入框，可录入/查看/编辑/清除，输入做格式校验 | §3 |
| 2 | 数据库未覆盖的域名：当前链路探测不可达时自动切到直连或代理 | §4、§5 |
| 3 | 默认策略：未录入的域名，国外链失败改直连；国内链失败改代理 | §4.2 |
| 4 | 改道示例要在实现里体现 | §6 |
| 5 | 匹配、探测、切换要准确可靠，有超时/重试/判定条件，不影响现有解析 | §5、§7 |

需求 1 是纯配置功能；需求 2~5 的核心矛盾是：

> **「按名单分流」是静态的，而「链路可达性」是动态的。**
> 一个域名今天该走代理，不代表十分钟后还该走代理。

---

## 2. 决策：静态归属 + 动态改道，两者分离

### 2.1 三个概念必须分清

| 概念 | 含义 | 谁决定 | 变不变 |
|---|---|---|---|
| **归属**（class） | 域名「应该」走哪条链 | 配置 + 名单（静态） | 只有改配置才变 |
| **首选**（preferred） | 由归属推导出的链路 | 归属（确定性映射） | 随归属变 |
| **当前**（active） | 实际生效的链路 | 健康探测（动态） | 随链路状态变 |

不分开这三个概念的后果是「配置」与「运行时」互相污染：
用户改了名单，探测结果却被当成配置的一部分；或者链路恢复后，
配置里还留着「已改道」的痕迹。分开之后：

- 配置文件只描述**意图**（归属）
- 状态文件（`/var/run/dnschain/health.state`）只描述**事实**（当前链路）
- 两者独立可查，页面同时显示，不一致就是「正在改道中」

### 2.2 归属的四个取值与优先级

```
custom-domestic   用户录入「国内域名」   ← 最高
custom-foreign    用户录入「国外域名」
db-foreign        命中 gfw/基础名单
uncovered         三个来源都没覆盖       ← 最低
```

**自定义优先于名单**是刻意的：用户手工录入就是要覆盖名单的自动判定。
若反过来，用户会遇到「我明明写了走直连，它还是走代理」这种无解困惑。

### 2.3 首选链路的映射

```
custom-foreign / db-foreign  → foreign   （代理出口 :5336）
custom-domestic / uncovered  → domestic  （直连出口 :5353）
```

`uncovered → domestic` 不是随便定的：**dnsmasq 的默认上游就是
`127.0.0.1#<entry_port>`**（`files/etc/config/dnschain` 与
`99-zz-dnschain` 都写死了这条）。所以未覆盖域名本来就走直连。
改道逻辑必须与这个事实一致，否则「不配置任何东西」与
「配置了框架」会表现出不同行为 —— 那是最难排查的一类不一致。

## 3. 自定义列表的实现

### 3.1 UCI 结构

```
config domains 'domestic'
    list domain 'www.baidu.com'

config domains 'foreign'
    list domain 'www.google.com'
```

两个**独立段**，不是同一段两个 list。理由：写回时同一段的两个 list
会被 CBI 互相覆盖（`NamedSection` 的 `parse` 按 section 整体写）。

### 3.2 三道校验闸

| 闸 | 位置 | 作用 |
|---|---|---|
| ① 页面 | `general.lua` 的 `validate_domain()` | 用户敲错时立刻看到 |
| ② 脚本 | `dc_domain_valid()` | 兜住直接 `uci set` 或从备份恢复 |
| ③ 自检 | `dnschain-health check` / selftest 第 17 项 | 事后可查 |

页面那道**刻意不比脚本更严**。页面校验写得过于复杂会误拒合法域名
（典型是 `xn--` 形式的 IDNA —— `--` 在 punycode 里是正常字符，
拦它会把整类中文域名拒掉）。所以页面只拦「明显不对」的形态，
权威判定在脚本。

### 3.3 格式规则（`dc_domain_valid`）

- 总长 ≤ 253，每个标签 1..63
- **至少两级**（单标签是主机名；`//` 是 dnsmasq 的「无点名字」特殊写法，
  混进来会改变语义）
- 标签只允许 `a-z 0-9 -`，不以 `-` 开头/结尾
- 顶级域：纯字母且 ≥2 位，或 `xn--` 前缀
- **不接受通配符**：`server=/域名/` 是标签后缀匹配，
  用户写 `*.example.com` 会得到一条永远匹配不到的规则，
  而页面上看不出任何异常

### 3.4 分流结果

| 归属 | dnsmasq 规则 | nftset | 效果 |
|---|---|---|---|
| 自定义国内 | `server=/域名/127.0.0.1#5353` | `china` | 解析走直连，IP 入直连集 |
| 自定义国外 | `server=/域名/127.0.0.1#5336` | `blacklist` | 解析走代理，IP 入代理集 |
| 数据库国外 | 同上 | `blacklist` | 同上 |
| 未覆盖 | 不写规则 | — | 落到 dnsmasq 默认上游（直连） |

`nftset` 目标集**先探测再写**（`dc_nftset_exists`）：SSR-Plus 未启用时
`ss_spec` 表根本不存在，此时写 `nftset=` 会让 dnsmasq 每解析一个域名
都尝试写集合并失败，在日志里刷错。宁可少写一行。

## 4. 自动改道的实现

### 4.1 核心规则（一句话）

> **首选链不通，且另一条链通 → 切到另一条链。**

### 4.2 两条需求规则如何落到这一句上

| 需求原文 | 对应场景 | 首选 | 另一条 | 结果 |
|---|---|---|---|---|
| 「访问国外链路失败则自动改为直连」 | 数据库国外域名 | `foreign` | `domestic` | 切直连 |
| 「访问国内链路失败则自动改为代理」 | 未覆盖域名 | `domestic` | `foreign` | 切代理 |

两条规则不是两个 if 分支，而是**同一个判定的两个实例** ——
因为「首选」已经由归属决定。这样加第三类域名时不需要再改判定逻辑。

### 4.3 判定状态机

对每个观测域名：

```
情形 A：当前 == 首选
    r_pref 通        → fail=0，保持
    r_pref 不通      → fail++；若 fail ≥ fail_threshold 且 r_other 通 → 改道
情形 B：当前 != 首选（已改道）
    r_pref 通        → ok++；若 ok ≥ recover_threshold 且 停留 ≥ min_dwell → 回切
    r_pref 不通      → ok=0，保持现状
双链都不通           → 不改道，标记 both-bad
```

**为什么双链都不通时不改道**：那不是分流问题，是链路故障。
改道只会把「两条链都坏」伪装成「一条链能用」，掩盖真正的问题。
页面把 `both-bad` 单独标红，直接提示「先查 dnsproxy 与代理」。

### 4.4 阈值默认值与理由

| 参数 | 默认 | 理由 |
|---|---|---|
| `timeout` | 2s | BusyBox `nslookup` 无 `-timeout`，框架自实现硬超时；2s 覆盖跨境 RTT 且一轮 10 域名可控 |
| `retries` | 2 | 单次 UDP 丢包常见；不重试会让改道变成随机行为 |
| `fail_threshold` | 2 轮 | 避开单轮抖动（一轮里可能两个域名各丢一次包） |
| `recover_threshold` | 3 轮 | 链路临界时反复横跳，每次横跳都改一次 servers-file |
| `min_dwell` | 120s | 同上，另加时间维度的下限 |
| `interval` | 60s | 小于 15s 会被抬到 15s（一轮探测本身 3~10s，更短只会重叠） |

### 4.5 观测列表，不做全量探测

全量（3.5 万域名）一轮要几小时，也会把 dnsmasq 与 dnsproxy 打满。
故只探测 `health.watch` 里的域名（默认国内外各 4 个基准站点）。
清空后自动回落到内置基准集 —— 空列表意味着永不探测、页面永远
「无数据」，用户会以为功能坏了。

**这是本设计明确的取舍**：改道只对观测域名生效，
其余域名仍按静态归属走。理由是「可观测性」比「全覆盖」更重要：
一个能说清楚「这 8 个域名现在走哪」的系统，
比一个「什么都在改但什么都看不见」的系统更可靠。

## 5. 改道的生效通道：`--servers-file` + SIGHUP

### 5.1 为什么不能用静态片段

`dnschain-split.conf` 通过 `--conf-dir` 加载。**实测（AGENTS §4.4）
dnsmasq 的 `reload`（SIGHUP）不重读 conf-dir** —— 改它必须
`restart`，代价约 3 秒解析中断。改道是可能每分钟发生的事，
绝不能走 restart。

### 5.2 采用的通道

dnsmasq 的 `--servers-file` 在收到 SIGHUP 时会被**重新读取**
（`dnsmasq.c` 的 `EVENT_RELOAD` 分支显式调用 `read_servers_file`）。
于是：

```
改道 → 重写 /var/etc/dnschain/watch.servers → kill -HUP dnsmasq
```

不重启、不清缓存、不影响未观测的域名。

OpenWrt 侧通过 UCI 下发：`dhcp.@dnsmasq[0].serversfile`，
由 `dnsmasq.init` 转成 `--servers-file`（`files/etc/uci-defaults/99-zz-dnschain`
首刷即写，`init.d/dnschain` 每次启动校验）。

### 5.3 硬约束：一个域名只能有一处 `server=` 声明

若同一个域名同时出现在静态片段与 `watch.servers` 里，
dnsmasq 会把两条 `server=` 当作**候选**（不是后者覆盖前者），
改道就退化成「随机走一条」，而且两条链都能解析时完全看不出问题。

因此 `dc_gen_dnsmasq_split()` **必须**从静态片段里排除观测域名。
selftest 第 18 项专门查这个重叠。

### 5.4 通道就绪性必须验「进程参数」

只配 UCI 不生效是存在的（dnsmasq 未重启、或进程被别处启动）。
页面「改道通道」一栏读 `/proc/<pid>/cmdline` 查 `--servers-file`，
selftest 第 19 项同样检查。这是「改道看起来成功、实际没生效」
的唯一可靠判据。

## 6. 需求第 4 条：改道示例在实现里的体现

单测（`tools/check-dnschain-lua.py` 之外的 dash 单测）逐条覆盖：

```
场景 A：github.com（db-foreign，首选 foreign）国外链 TIMEOUT、直连 OK
  第 1 轮 → 不改道（未达阈值），状态 probe:TIMEOUT
  第 2 轮 → 改道到 domestic，状态 switch:TIMEOUT->OK
          watch.servers 出现 server=/github.com/127.0.0.1#5353

场景 B：www.qq.com（uncovered，首选 domestic）直连 TIMEOUT、代理 OK
  第 1 轮 → 不改道
  第 2 轮 → 改道到 foreign
          watch.servers 出现 server=/www.qq.com/127.0.0.1#5336

场景 C：两条链都 TIMEOUT → 不改道，状态 both-bad

场景 D：改道后首选链恢复 → 连续 2 轮成功 + 驻留达标 → 回切
        状态 recover:OK

场景 E：自定义列表里的域名 → 状态 fixed:OK，永不改道
```

场景 A 对应需求第 4 条前半句（「表内未收录域名访问国外不通时改走直连」），
场景 B 对应后半句（「访问国内不通时改走代理」）。

> 注：需求原文说「表内未收录域名」，而场景 A 用的是数据库命中域名。
> 两者在改道机制上**完全一致** —— 因为改道只看「首选 vs 另一条」，
> 不看归属来源。区别只在首选是哪个。故用 A 演示「国外不通改直连」
> 的机制，B 演示「国内不通改代理」，合起来覆盖两条规则。

## 7. 对现有功能的影响

| 现有行为 | 影响 | 验证方式 |
|---|---|---|
| 静态分流（gfw 名单） | 不变，只是生成时多排除观测域名 | selftest 18 |
| dnsmasq 缓存（唯一缓存层） | 不变；SIGHUP 不清缓存 | selftest 16 |
| dnsproxy 双实例 | 不变；改道只换 dnsmasq 的上游指向 | selftest 1~15 |
| 开机时序 | 健康守护先等一轮 interval 再探，避开开机风暴 | `dc_health_cycle` 的实例就绪检查 |
| SSR-Plus 兼容 | 不变；`nftset` 目标集先探测再写 | `dc_nftset_exists` |
| 解析中断 | 保存配置时 restart 一次（约 3 秒，与既有行为相同）；**改道不中断** | `dc_health_cycle` 内无 restart 断言 |

## 8. 页面与图

### 8.1 为什么新增「域名」tab

三件事在逻辑上是一条链：**我录了什么 → 它会怎么走 → 现在哪个不正常**。
拆成多个 tab 时用户得来回切才能对上，而「配置」与「诊断」分离会让
「为什么它没按我写的走」这个问题变成跨页推理。

### 8.2 两张图的职责分工

| 图 | 回答的问题 | 形态 |
|---|---|---|
| **判定链路图** | 这个域名会怎么走、在哪一步出问题 | 上下两段：归属→首选 / 探测→结论 |
| **改道状态图** | 现在哪些域名不正常、该查什么 | 一个根分五种状态，每种带计数、清单与下一步 |

**状态分五档而不是「正常/异常」两档**：把「已自动改道并恢复可用」
与「两条链都不通」混在一起是错的 —— 前者不需要人介入，
后者必须人介入。分档之后红黄绿各自含义唯一。

### 8.3 图的实现约束（都踩过）

- 连线用三次贝塞尔 `C`。直角折线在分叉处是硬拐角，视觉上像断链
- 控制点 `dx ≤ (x2-x1)/2`，否则曲线自交成扭结
- 节点必须有填充，`fill="none"` 时连线从节点内部透出
- marker id 必须带前缀（`dcrt` / `dcst`）—— 同页两张 SVG，
  id 是文档级全局的，同名会全部解析到第一个定义（颜色串掉）
- 动态文本必须 HTML 转义 —— 域名或原因含 `& < >` 会让整张图解析失败

这些约束由 `tools/render-dnschain-diagrams.py` 做纯几何校验
（越界、重叠、控制点交叉、marker 前缀、转义），几秒出结论，
不依赖浏览器。

## 9. 被否决的方案

### 9.1 否决：用 dnsproxy 的 `[/域名/]` 做动态分流

理由与 ADR-0005 相同：17767 条 `[/域名/]` 会让 dnsproxy 为每域名
注册一条 reserved 上游，资源耗尽 → `connection timed out`。
实测过，不可行。

### 9.2 否决：改道时 restart dnsmasq

3 秒解析中断，而改道可能每分钟发生。不可接受。

### 9.3 否决：全量探测所有域名

一轮几小时，且会把 dnsmasq 与 dnsproxy 打满。见 §4.5 的取舍说明。

### 9.4 否决：把「已改道」持久化到 UCI

断电前的「已改道」不该在下次开机继续生效 —— 那时链路可能是好的。
状态放 `/var/run`，重启即重算。这也让「配置」与「事实」保持分离（§2.1）。

### 9.5 否决：页面用嵌套 `<form>` 做「单域名解释」

CBI 的 map 模板已把整页包在 `<form method="post">` 里。
内层 `<form>` 是非法 HTML，浏览器会丢掉内层标签 ——
「解释」按钮实际提交的是外层表单（= 触发保存）。
实测症状：点「解释」看到「配置已保存」。改用普通 input + button，
由 `dnschain.js` 绑定点击后自己跳转（含拦截 Enter）。
