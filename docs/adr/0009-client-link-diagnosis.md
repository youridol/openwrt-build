## 1. 背景

用户提出：

> 我需要在 DNS 分流插件中添加在线读取抓包主机链路信息分析客户机不通的链路后处理

具体场景是**某些移动 App 混合国内外的资源打不开**（举例：拓竹 / Bambu App）。

现有诊断能力的缺口：

| 能力 | 现状 |
|---|---|
| 路由器自身视角的诊断 | 有（自检 20 项：DNS 路径、进程、端口、规则、双栈） |
| **客户机视角**的诊断 | **无** |
| 域名级失败记录 | 无（`logread` 环形缓冲几分钟就冲掉） |
| 自愈动作 | 无（v0.22.0 删掉了自动改道） |

**关键区别**：自检 20 项全绿 ≠ 客户机没问题。实测中
`www.baidu.com` 等域名在路由器侧全部正常，而某台客户机仍可能打不开某个 App。
两者是**不同视角**，不能互相替代。

## 2. 事实基础（路由器实测，2026-10-25）

设计前先取的事实，避免靠猜：

| 事实 | 实测值 |
|---|---|
| `dnsmasq` 的 `logqueries` | **已是 1**（查询日志已开） |
| `log-facility` | `syslog`（v0.14.8 修好，日志可用） |
| 日志条数 | 实测 998 条可用 |
| `tcpdump` | **未安装**（CI 未启用 `CONFIG_PACKAGE_tcpdump`） |
| `conntrack` / `nft` / `logread` | 都有 |
| CPU | Intel Celeron N2930 @ 1.83GHz（4 核低功耗） |
| `logread` 环形缓冲 | **几分钟到几十分钟就冲掉**（实测抓完 Bambu 日志几分钟后已消失） |

### 2.1 日志格式（一条记录含客户机 + 域名 + 答案）

```
dnsmasq[1]: 187349 192.168.3.193/35143 query[A] asia.pool.ntp.org from 192.168.3.193
dnsmasq[1]: 187349 192.168.3.193/35143 forwarded asia.pool.ntp.org to 127.0.0.1#5353
dnsmasq[1]: 187349 192.168.3.193/35143 reply asia.pool.ntp.org is 168.144.182.136
```

字段：`<查询ID> <客户机IP>/<源端口> <动作> <域名> [from <IP> | to <上游> | is <答案>]`。

**一个查询 ID 把「谁问的 / 问什么 / 转发给谁 / 答了什么」串起来**，这是本功能的数据基础。

### 2.2 实测案例：拓竹 App（`192.168.3.203`，ALN-AL80）

| 域名 | 走向 | 答案 | 判定 |
|---|---|---|---|
| `makerworld.bblmw.cn` | `:5353` 直连 | `124.227.185.44`（广西电信） | 正常 |
| `public-cdn.bblmw.cn` | `:5353` 直连 | `124.227.185.30` | 正常 |
| `geo-drcn.platform.dbankcloud.cn` | `:5353` 直连 | — | 正常 |

同时观察到两条 `NODATA-IPv6`：

```
reply makerworld.bblmw.cn.w.kunlunaq.com is NODATA-IPv6
reply public-cdn.bblmw.cn.w.kunlunaq.com is NODATA-IPv6
```

**这是正常行为**（手机先查 AAAA 拿到「无 IPv6 记录」，再查 A 成功），
不是故障。这条记录写进 ADR 是为了防止后来者把它误判成失败
（AGENTS.md §5.1 记载过同类误判：把 `EMPTY` 当失败会得出「国内也全挂」的错误结论）。

### 2.3 实测案例：Bambu 打印机的真实 IP 是 `192.168.3.185`（不是 `.230`）

| 检查项 | 实测 |
|---|---|
| `api.bambulab.cn` | 直连 → `119.0.68.19` ✅ |
| `device-file.bambulab.cn` | 直连 → `180.163.123.186`（阿里云上海 OSS）✅ |
| MQTT 控制通道 | `tcp 47.100.40.179:8883` 阿里云上海 ✅ |

**它的 DNS 与主链路都健康。** 这说明「App 打不开」未必是 DNS 问题 ——
见 §6 的边界声明。

### 2.4 随机 MAC 的证据

`/tmp/dhcp.leases` 实测：

```
72:62:84:8a:f3:8c  192.168.3.203  ALN-AL80      ← 第2位 2 = 本地管理位（随机）
ae:fb:34:6e:fa:cd  192.168.3.202  iPhone        ← 第2位 e = 本地管理位（随机）
f6:d9:87:82:9b:dd  192.168.3.232  vivo-Y52s     ← 第2位 6 = 本地管理位（随机）
5c:e5:0c:b2:b1:ee  192.168.3.206  zhimi-air...  ← 第2位 c = 全局唯一（真实）
```

**MAC 是随机的，用它认设备会失效。** 稳定的标识是 **IP**（租期内固定）
与 **主机名**（设备自报，不受随机 MAC 影响）。

## 3. 决定

### 3.1 数据来源：日志优先，抓包二期

| 数据 | 来源 | 阶段 |
|---|---|---|
| 客户机查了什么域名 | `logread`（dnsmasq 日志） | 一期 |
| 客户机收到什么答案 | 同上 | 一期 |
| 哪个客户机 | 同上（`from <IP>`）+ `/tmp/dhcp.leases` 查主机名 | 一期 |
| 走哪条链 | 同上（`forwarded ... to 127.0.0.1#5353/#5336`） | 一期 |
| TCP 连不上 / TLS 失败 / 重传 | **需要 tcpdump** | 二期 |

**为什么一期不用 tcpdump**：

- `tcpdump` 当前未装，引入需 +150KB 进固件
- N2930 是低功耗 4 核，高速流量抓包会掉包
- pcap 写 tmpfs 占内存
- **DNS 层的四段里前三段日志完全够用**，只有「DNS 成功但 TCP 连不上」必须抓包

### 3.2 判定四段链路

客户机一次解析/访问穿过的环节，以及日志能否覆盖：

| 段 | 失败表现 | 日志能否判定 |
|---|---|---|
| ① 客户机 → dnsmasq:53 | 无响应，日志里**没有 query 行** | ✅ 靠「有请求但无 reply」反推 |
| ② dnsmasq → dnsproxy | `forwarded` 后无 `reply` | ✅ 有 |
| ③ dnsproxy → 上游 | `SERVFAIL` / `upstream timed out` | ✅ 有 |
| ④ 客户机 → 目标 IP | DNS 正常但 TCP 失败 | ❌ **二期 tcpdump** |

### 3.3 客户机识别：IP + 主机名，不用 MAC

- 主键：**IP**
- 显示：`192.168.3.203 · ALN-AL80`
- 主机名来源：`/tmp/dhcp.leases`（dnsmasq 自己写，格式稳定）
- **不显示 MAC 作为设备身份**；若 MAC 是本地管理位（第 2 位为 `2/6/a/e`），
  标注「随机 MAC」而非当成标识

### 3.4 失败判据

| 判据 | 阈值 | 说明 |
|---|---|---|
| 触发自愈 | 同一域名 **5 分钟内累计 ≥3 次** `SERVFAIL` / `timed out` | 正常重试不触发 |
| 自愈防抖 | 同一故障 **30 分钟内最多 3 次** | 防止重启循环 |
| 记录保留 | 默认 **1 小时**，条目上限默认 **500 条**，均可自定义 | 用户明确要求可配 |

**明确不算失败**（写进代码注释，防误判）：

- `NODATA-IPv6` —— 手机正常的 AAAA 探测
- `NXDOMAIN` —— 域名确实不存在
- `query is duplicate` —— dnsmasq 的去重提示
- `<CNAME>` —— 中间跳，后面还有最终答案

### 3.5 分级自愈（逐级升级，能用小的不用大的）

| 级别 | 动作 | 中断 | 幂等 | 自动 |
|---|---|---|---|---|
| **L1** | `dnschain-selftest flush`（SIGHUP dnsmasq） | **零** | ✅ | ✅ |
| **L2** | `dnschain-selftest apply`（重建 split.conf） | 零～极短 | ✅ | ✅ |
| **L3** | 重启 dnsmasq | 实测 **3 秒** | ✅ | ✅（受时间窗与限频约束） |
| **L4** | 改域名归属（写入自动列表） | 零 | ✅ | ✅（见 3.6） |

**升级顺序**：L1 → 无效 → L2 → 无效 → L3。绝大多数故障 L1 就够。

**时间窗**：自动自愈默认**每小时最多 1 次**，可自定义。用户明确要求
「自动+手动+时间窗，可自定义时间，默认 1 个小时自动自愈一次」。
手动触发不受时间窗限制（用户明知可以断网才会点）。

### 3.6 改归属（L4）：分区隔离，手写优先

v0.22.0 删掉自动改道的教训是**自动动作静默覆盖正确配置**：

```
split.conf:    server=/wikipedia.org/127.0.0.1#5336      ← 正确（代理）
watch.servers: server=/www.wikipedia.org/127.0.0.1#5353  ← 自动改道写入（直连）
→ dnsmasq 把两条当候选 → www.wikipedia.org 返回 31.13.106.4（Facebook 的 IP）
```

因此 L4 **不直接改用户手工维护的两个列表**，而是分区隔离：

| 列表 | 谁写 | 优先级 |
|---|---|---|
| `dom_domestic` / `dom_foreign` | **用户手工** | **高**（永不被自动改写） |
| `dom_auto_domestic` / `dom_auto_foreign` | 系统自动 | 低（用户手写同域名时自动让位） |

**用户手工录入的域名永不被自动改写。** 系统只自动处理
`CLASS=uncovered`（未被任何列表覆盖）的域名。

**每次自动调整都留审计痕迹**，页面可逐条撤销（`autofix_log`）。

### 3.7 页面形态：两层结构，独立 section

放在「状态」tab，作为独立 section「客户机链路诊断」，排在
「当前状态」之后、「DNS 分流去向」之前（ADR-0007 判据：这是「结果」不是「参数」）。

**三块内容 + 九个可配置项**：

```
① 客户机列表
   客户机 IP        主机名       查询数  失败数  最近失败    最近域名
   192.168.3.203   ALN-AL80       49      0      —         -

② 实时查询链路（核心，含成功查询）
   时刻      客户机            域名                        结果      链路   答案
   17:00:45  192.168.3.203    makerworld.bblmw.cn         成功      —     124.227.185.33
   17:00:48  127.0.0.1        downloadcfpro.xn--...        无此类型   —     NODATA-IPv6

③ 失败时间线（排障用，只列失败）
   时刻      域名                状态      原始       失败段
   16:02:11  makerworld.bblmw.cn  上游失败  SERVFAIL   ③ 上游明确失败
```

**② 是用户要求的「客户机发起的查询完整链路」** —— 它记**全部查询**，
不分成功失败。只看失败列表回答不了「这台设备刚才查了什么、走的哪条链」。

### 两级导航（用户第二轮要求）

用户明确要求「第一级是当前在线主机，选定点击主机后转到第二级」。

```
第一级  /dns_chain                       在线主机列表 + [查看链路]
第二级  /dns_chain?dc_host=<IP>          该主机的完整链路
第三层  /dns_chain?dc_host=<IP>&dc_dom=<域名>   该域名的链路详情
```

**在线主机取自 ARP 邻居表**（`ip neigh show` 的 REACHABLE/STALE/DELAY），
不是「保留期内有记录」—— 后者会把已下线设备也列为在线。

第二级的「域名链路详情」回答用户要的「打开主域名后跳转到哪里、
到哪一步出问题」：

```
✅ 全链路正常，未发现失败
从哪里来：客户机 192.168.3.238
第一跳：本机 dnsmasq  dnsmasq:53（唯一缓存与分流层）
第二跳：上游实例      127.0.0.1#5353 ×20
最终答案              113.105.155.193
归属判定              uncovered → domestic
```

「到哪一步出问题」按段号推断（§3.2 四段）：`OK=0` → 全失败；
`servfail` → 第 ③ 段；`noreply` → 第 ② 段。

### 搜索（按域名关键词）

`search <关键词> [IP] [N]` 子命令 + 页面输入框，不区分大小写子串匹配，
可叠加当前主机收窄。回车改为带 `dc_q` 的 GET —— 直接回车会触发
CBI 的整页 POST（= 保存配置），用户只是想搜索。

### 刷新必须保留 URL 参数

自动/手动刷新都带 `location.search`。实测踩过：不带时每次刷新跳回
第一级，用户正在看的第二级详情被踢掉。

**九个可配置项**（页面输入框，保存即写 UCI）：

| 键 | 含义 | 默认 |
|---|---|---|
| `enabled` | 启用诊断 | 1 |
| `autofix_enabled` | 启用自动自愈 | 1 |
| `interval` | 扫描间隔（秒） | 60 |
| `fail_threshold` | 失败阈值（次） | 3 |
| `fail_window` | 失败判定窗口（秒） | 300 |
| `flow_retain_sec` | **查询流水保留（秒）** | 600 |
| `flow_retain_max` | **查询流水条目上限** | 1000 |
| `retain_sec` | 失败记录保留（秒） | 3600 |
| `retain_max` | 失败记录条目上限 | 500 |
| `autofix_interval` | 自动自愈最小间隔（秒） | 3600 |

用户明确要求「可自定义时间和条目数量，默认 1 小时」——
失败记录默认 3600 秒，查询流水默认 600 秒（流水量大）。

**与自检的关系**：独立成块，但在自检里加一条汇总项
「客户机失败链路 N 条」，让「自检全绿但用户打不开」这个矛盾可见。

## 4. 被否决的方案

### 4.1 用 MAC 识别客户机

否掉理由：实测三台移动设备的 MAC 都是本地管理位（随机 MAC），
用 MAC 认设备会失效。用户最初要求「IP+主机名+MAC」的理由正是
「移动设备会随机 MAC」—— 而随机 MAC 恰恰证明 MAC 不可用作身份。

### 4.2 一期就引入 tcpdump

否掉理由：见 §3.1。一期用日志能覆盖 4 段里的前 3 段，先验证判据准确性，
避免一上来就背着性能包袱。二期再加。

### 4.3 L4 直接改用户的手工列表

否掉理由：会重蹈 v0.22.0 覆辙（静默覆盖正确配置）。改为分区隔离 + 审计可撤销。

### 4.4 自动自愈不限频

否掉理由：若故障持续存在（如上游节点挂了），会反复重启 dnsmasq，
每次让**所有客户机**断 3 秒，而问题可能根本不在 dnsmasq。
用户原话「随时都可以断」是针对**手动**触发（明知可以断才点），
不等于允许自动无限重启。

### 4.5 落盘到 flash

否掉理由：频繁写 flash 会损伤存储。用 tmpfs（`/var/run/dnschain/`），
重启即失，但失败记录量小（正常时几乎为零），tmpfs 占不了多少内存。

## 5. 后果与约束

### 5.1 必须新增的依赖与权限

| 项 | 内容 | 理由 |
|---|---|---|
| ACL read | `logread`（`/sbin/logread`） | 读 dnsmasq 日志 |
| ACL read | `/tmp/dhcp.leases` | 查主机名 |
| ACL write | `/var/run/dnschain/*`（已有） | 写失败记录与审计日志 |
| CI CONFIG | **一期不需要**（无 tcpdump） | 二期再加 `CONFIG_PACKAGE_tcpdump` |

### 5.2 失败记录落盘（tmpfs）

```
/var/run/dnschain/client-fail.log      失败事件（JSON 行或 TSV）
/var/run/dnschain/autofix.log          自动自愈审计（可逐条撤销）
/var/run/dnschain/autofix.state        上次自愈时间（用于时间窗与限频）
```

- 默认保留 1 小时、上限 500 条，**均可自定义**
- 超过上限时丢最旧的
- 重启即清空（tmpfs）

### 5.3 不能覆盖的场景（必须明说）

**「DNS 正常但 App 仍打不开」一期不覆盖。** 实测拓竹设备的
DNS 与主链路全部健康，说明这类问题的根因在更上层（证书、鉴权、
区域限制、设备固件）。一期只能告诉用户「DNS 层正常，问题在更上层」，
**不能给出错误的修复建议**。

### 5.4 与自检 20 项的关系

两者视角不同，**不得互相替代**：

| | 自检 20 项 | 本功能 |
|---|---|---|
| 视角 | 路由器自身 | 客户机 |
| 数据 | 进程/端口/规则/配置 | dnsmasq 日志 |
| 结论 | 「路由器自己没问题」 | 「某台客户机有问题」 |

自检加一条汇总项「客户机失败链路 N 条」，让两者的矛盾可见。

---

## 6. 验证计划

实现后必须做的验证：

| 项 | 方法 |
|---|---|
| 日志解析正确性 | 用实测日志样本（§2.1）跑解析，逐字段核对 |
| `NODATA-IPv6` 不误判 | 构造含该行的样本，断言**不**记为失败 |
| 阈值触发 | 构造 3 条失败 → 断言触发；2 条 → 断言不触发 |
| 时间窗 | 构造「刚自愈过」的状态 → 断言 1 小时内不再自动 |
| 手写优先 | 手工加 `x.com` 到 `dom_foreign`，自动判定要改直连 → 断言不覆盖 |
| 分级升级 | mock L1 无效 → 断言升级到 L2 |
| 审计可撤销 | 自动改 2 条 → 撤销 → 断言 UCI 恢复 |
| 客户机识别 | 随机 MAC 设备 → 断言显示主机名而非 MAC |

## 7. 分期

| 期 | 内容 |
|---|---|
| **一期** | 日志解析 + 四段判定 + 客户机列表/时间线 + L1–L4 自愈 + 审计撤销 |
| **二期** | `tcpdump` 抓包补第 ④ 段（TCP/TLS 层），按需短时抓取 |

一期完成即可覆盖用户 80% 场景（DNS 层失败），二期补「DNS 正常但连不上」。
